How Deal Hunter works

← back to the dashboard · source on GitHub ↗

A hunt reads the deal-flow inbox, extracts candidate properties, enriches the survivors with public data, underwrites them against a personalized buy box, and publishes the verdicts here. No servers, no paid data — the whole system is a Python package, a committed SQLite file, and a static page.

How it runs today: hunts are driven interactively from a Claude Code session using the Gmail connector — no API key, no stored mail credentials. The same pipeline/ code does every deterministic step. A GitHub Actions workflow is committed and runs the test suite plus the dashboard redeploy on every push; its daily schedule: trigger is deliberately commented out until the API-key and OAuth secrets are provisioned, so the automated path is one uncommented block away rather than a claim this page can't back up.

The pipeline

1
Ingest

A dedicated inbox receives only deal flow from five senders (an agent covering all deal types + four STR-focused newsletters), read through the Gmail connector interactively or a read-only OAuth scope under cron. A processed-email registry keyed by message ID makes ingestion idempotent, so re-running a hunt never double-counts a property.

↓
2
Extract

Claude parses messy newsletter HTML into structured candidates: address, price, and the seller's claimed numbers — which are tagged seller-claimed and never trusted directly.

↓
3
Dedupe

Normalized-address hashing against the SQLite database, so a property pitched by three newsletters is analyzed once.

↓
4
Kill filter

Deterministic first-pass checks that spend zero API calls: price ceilings the capital can't reach, confirmed non-destination markets, deals that fail the seller's own optimistic math. Most emailed deals die here, for free.

↓ survivors only
5
Enrich

Redfin (via OpenWebNinja) is the primary structured source — real tax bills, HOA, listing status, Redfin estimate, and the listing photo shown on each card — plus RentCast for rent estimates and valuations, STR revenue estimates via web search, county appraisal-district records, live investment mortgage rates, and a short-term-rental ordinance check that is never auto-cleared. Enrichment runs on kill-filter survivors only, so a 100-call/month free tier covers a whole month of deal flow.

↓ paywalled teasers only
5b
Identify

Three of the newsletters tease their headline deal without an address. A deterministic Redfin search matches the stated market on price (±1.5%) and exact beds/baths — one survivor means high confidence, two means ambiguous and is recorded as such. Every derived address carries its evidence and is marked research-derived until a human verifies it.

↓
6
Score

Pure, unit-tested Python: cap rate, cash-on-cash, DSCR, GRM, break-even occupancy → three tier-specific buy boxes → four-pillar grading → hard disqualifiers → tax-strategy triggers → PASS / BORDERLINE / FAIL plus a 0–100 composite score.

Geography is part of the underwriting, not a filter bolted on after. Priority markets — established mountain destinations that are metro-fed, short-term-rental friendly, and inside a drive-time cap of home — carry a composite bonus, so an equally profitable deal in a reachable market outranks one that isn't. Each region stores its own drive time, which makes the cap a number in a config file rather than a hand-kept list of towns.

↓
7
Publish

Processed mail is labelled in Gmail — Deal Hunter/Scored on everything triaged, Deal Hunter/Surfaced on the emails that actually produced a PASS or BORDERLINE — so the inbox mirrors the database. Nothing is archived or marked read. The database is committed (git history is the audit trail), a ranked digest can post as a GitHub issue, and this dashboard redeploys.

Design decisions

  • LLM only where language is messy; code everywhere math must be right. Claude does parsing and web-search synthesis. Every metric, threshold comparison, and verdict is deterministic, unit-tested Python — a scoring engine you can't reproduce is a vibe, not an underwriting tool.
  • Judgment calls are flagged, never automated. Borderline destination-market status, which BORDERLINE deals to act on, rehab estimates, and final STR-legality verification are surfaced explicitly and left to the human. The pipeline makes the judgment call cheap; it doesn't make it.
  • Personal financial data never enters the repo. Scoring reads a gitignored private profile; the repo ships a sanitized example so it runs for anyone. This page shows verdicts and metrics — never income, capital, or tax numbers.
  • The strategy itself is versioned. The investment framework is markdown in the repo. When an assumption proves wrong, the fix is a commit with a diff history.

Why v2 exists: the project started as parallel AI-partner experiments that drifted into contradiction — different LTV ceilings, tax law that had been superseded (the OBBBA made 100% bonus depreciation permanent), different capital plans. An audit established precedence, filled the gaps neither version covered (a first-pass kill stage, STR operating-expense defaults), and the reconciled framework became the single source of truth the pipeline enforces.
